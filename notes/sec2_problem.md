# 第2章 問題の定式化（研究非依存・自己導出）

## 2.1 二つのコスト、二つのフェーズ

Transformer 推論は性質の異なる二つのフェーズを持つ。両者のボトルネックは
別物であり、この区別を落とすと「O(n^2) を解いた」という主張の意味が曖昧になる。

- Prefill（プロンプト処理）: 長さ n を一括投入。Attention は n×n 行列を要し、
  計算量 O(n^2 d)。演算強度が高く compute-bound。
- Decode（自己回帰生成）: 1 トークンずつ。ステップあたりの Attention は
  O(n d)。しかし毎ステップ KV キャッシュ全体を HBM から読む必要があり、
  演算強度が O(1) に潰れるため memory-bandwidth-bound。

したがって:
- 「O(n^2)」が痛いのは主に prefill と学習時。
- 「KV キャッシュ」が痛いのは主に decode 時とバッチ多重度。

## 2.2 KV キャッシュのサイズ式

  S_kv = 2 * L * H_kv * d_head * n * B * b   [bytes]

  L: 層数, H_kv: KV ヘッド数, d_head: ヘッド次元, n: 系列長,
  B: バッチサイズ, b: 要素バイト数, 先頭の 2 は K と V。

重要な性質:
- n について線形。だが係数が大きい。
- B について線形 → スループット最大化とコンテキスト長がメモリを奪い合う。
- モデル重みが定数なのに対し KV は可変 → 長文・大バッチでは KV が支配的になる。

## 2.3 デコードのローフライン

1 トークン生成に必要な HBM 転送は概ね「重み + KV キャッシュ」。
演算は行列ベクトル積が中心で FLOPs/byte が小さい。よって

  t_step ≳ (W + S_kv) / BW_HBM

生成速度の上限は帯域幅で決まる。ここから二つの帰結が出る:
(a) KV を減らすことは、そのまま生成レイテンシの短縮になる。
(b) バッチを増やすと重み読み出しは償却されるが KV は償却されない。
    → KV 削減はスループット向上とレイテンシ短縮を同時に達成しうる稀な軸。

## 2.4 「解いた」の四つの意味（本レビューの評価軸）

本レビューは各手法を次の 4 軸で分類する。混同されがちな軸である。
  A. 漸近計算量 (FLOPs) を下げたか
  B. メモリ実体化 (materialization) を回避したか
  C. 状態サイズ（KV/再帰状態）を定数または劣線形にしたか
  D. 出力が厳密 (exact) か近似 (approximate) か

例: FlashAttention は A を下げない、B を達成、C は不変、D は厳密。
    Linformer は A を下げる、C も下げる、D は近似、しかし因果性と相性が悪い。
    この 4 軸で見ると、多くの論争は「別の軸の話をしていた」ことが分かる。
